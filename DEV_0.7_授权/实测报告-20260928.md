## 4. 实测中发现的问题

### 4.1 【已修·阻断级】交付包里的 .ps1 没有 BOM，用户双击「安装.cmd」装不上

**现象**（用户视角，直接在交付目录里跑 `安装.cmd`）：

```
tools\install.ps1:48 char:106
+ ... d-in manager to enable TianGong Toolbox (DEV 0.7.0), or restart CAD.'
The string is missing the terminator: '.
```

**根因**：仓库里所有 `.ps1` 都是 **UTF-8 无 BOM**，且正文有中文。Windows PowerShell 5.1 对无 BOM 文件
按**系统 ANSI（本机 GBK）**解码 → 中文变乱码 → 引号/花括号配对被打断 → 解析失败。
`安装.cmd`/`卸载.cmd`/`重新编译安装.cmd` 用的都是 `powershell.exe`（5.1），所以**三支全部失效**。
（用 PowerShell 7 跑同一份脚本没事 —— 这也是它一直没被发现的原因。）

**影响**：客户拿到交付包后无法安装、无法卸载、无法重新编译安装。实测受影响文件包括
`build.ps1`、`install.ps1`、`make-delivery.ps1`、`make-test-codes.ps1`、`mouse-e2e\01-start.ps1` 等。

**修法**：给 `DEV_0.7_授权\tools\**\*.ps1` 里**含非 ASCII 的 60 个脚本**统一加 **UTF-8 BOM**（纯 ASCII 的 19 个没动）。

**复验**（真·Windows PowerShell 5.1，`PSVersion=5.1.19041.6456`）：

```
tools\build.ps1        => PARSE-OK      tools\install.ps1        => PARSE-OK
tools\make-delivery.ps1=> PARSE-OK      tools\LicenseAdmin\make-test-codes.ps1 => PARSE-OK
```

并要求**实跑三支 .cmd**（见 4.2 后的验证）：`安装.cmd` → `Registered for current user: ...payload\TianGongCadSuite.dll`；
`卸载.cmd` → `Unregistered …`；`重新编译安装.cmd` → 先编译（正式构建）再注册，全部成功 ✅

> 教训：这个坑只在"用户机器上双击 .cmd"这条路径上才暴露，用 pwsh 7 手工跑脚本永远看不到。
> 建议以后交付前固定加一条检查，例如：
> `Get-ChildItem tools -Filter *.ps1 -Recurse | Where-Object { (Get-Content -Encoding Byte -TotalCount 3 …) -ne 'EF BB BF' }`。

### 4.2 【已修·阻断级】`重新编译安装.cmd` 的语法是 PowerShell 的，cmd.exe 不认

**现象**：

```
Processing -File '...\tools\build.ps1;' failed because the file does not have a '.ps1' extension.
```

**根因**：`make-delivery.ps1` 生成这一支时写成了一行：
`powershell.exe … -File "…\build.ps1"; if($LASTEXITCODE -eq 0){ … }` ——
`;` 和 `if(){}` 是 PowerShell 语法，但这一行是**由 cmd.exe 执行**的，整串被当成 `-File` 的实参，
于是文件名变成 `build.ps1;`。

**修法**：改成**分行的 cmd 语句**（`if errorlevel 1 ( … goto :eof )`），并在 `make-delivery.ps1` 里留了注释说明原因。

**复验**：重新生成交付包 → `重新编译安装.cmd` 实跑：

```
插件已编译：...\交付_DEV_0.7.0_20260928\build\TianGongCadSuite.dll  版本 0.7.0.0  正式构建
Registered for current user: ...\交付_DEV_0.7.0_20260928\build\TianGongCadSuite.dll
```
✅

正常跑完的批次**不会**留下进程（22:52、22:54 两批跑完就干净了），所以问题只在"停止/中途退出"这条路径上。
`FORMAT-CONVERT.md` 第 7 节写的是"点『停止』或工具被强杀时会一起结束，**不留僵尸进程**"，与实测不符。

**根因**：作业对象只装得住我们直接`Process.Start` 的 worker；worker 拉起的隐藏天工CAD 是
**DCOM 启动的服务进程**（`/automation -Embedding`），从 SCM 起来、父进程是 svchost，**不进作业**。
停止时作业被杀，没人再去 `Quit` 那个 CAD，它就成了孤儿。
（先按"父进程 = worker"写过一版，实测父进程恒为 svchost，判断永远不成立，已改成下面这种做法。）

**修法**（`src/FormatConvertForm.cs` 新增 `WorkerChildren`）：停止/关窗时在终止作业之后，按
**"命令行含 `/automation` + 创建时间不早于本次转换开始前 60 秒"** 精确回收，并在界面日志里写明
"已结束转换器拉起的隐藏 CAD（pid …）"。用户自己开的天工CAD 命令行里没有 `/automation`，不会被误杀。

**复验**：重新编译 → 重启 CAD → 跑 10 个文件的批次 → 25 秒后点「停止」：

```
停止后的进程：只有会话里的 16072（会话 CAD 活着 ✅），隐藏 CAD 已被回收 ✅
面板日志：已结束转换器拉起的隐藏 CAD（pid 7340）。
```

单元测试复跑仍然全绿（223 / 106 / 30 / 92，EXIT=0）。

> 仍未覆盖的边角：整个工具进程被**强杀**（任务管理器结束）时，作业对象会杀掉 worker，但那个
> DCOM CAD 还是收不到 —— 要彻底堵上得让 worker 把 CAD 显式加进作业（需要给作业起名并传进去）。
> 这条路径没测也没改，留给你决定。

### 4.4 【观察·未修】装配里开着检查面板再换文档，CAD 会弹「文档错误」

**现象**：`配孔检查` 面板开着（它持有当前装配的引用）时，从外部切换文档 → CAD 弹
`文档错误：无法找到或打开指定的文档。`，之后功能区点命令没反应（被模态框挡住）。
**规避**：先关面板再换文档就不复现；把模态框点掉也能继续。
这像是"关闭正在被面板引用的装配"引起的 CAD 侧行为，**不像插件逻辑错误**，但用户确实可能撞上，
建议在 `FormClosed`/切文档时主动放开 `assembly` 引用，或在面板上明确提示。

### 4.5 【观察】零件环境（顶层 .par）下按钮变灰，但界面渲染偶尔不一致

在只打开一个 `.par` 时：`配孔检查`、`批量排孔`、`四面生成内嵌板`、`型材自动填充`、`Lineup 模型标记` 按
`HasEditableContext`/`HasAssembly` 判定后**是灰的**（日志 `ContextProbe 打开的装配里没有匹配该零件的实例` 可自证），
点上去没反应 —— 符合设计。但功能区里 `自动打孔` 有时**画成可点的黑色**，点了也没反应，容易让人以为"点了没响应"。
两条路径的打孔命令本身在**装配上下文**下都实测通过（见 3.B 回归）。
